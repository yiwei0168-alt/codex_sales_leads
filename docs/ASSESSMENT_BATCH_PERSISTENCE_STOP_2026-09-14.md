# 阶段106：评分批次持久化失败后停止新增付费工作

评分器原先在一个已完成批次的缓存保存失败后继续请求后续批次。如果后续请求因预算或未知费用暂停，评分节点尚未形成图检查点，先前的有效结果就只能依赖已经失败的缓存写入。现改为：发布已完成结果失败后，停止领取**尚未开始**的批次；同批缺项修复也暂缓。未开始公司的评分状态为 `retry-required`，不是业务不合格。已经在途的并发请求会完成并纳入本节点结果，不声称可以撤销在途费用。已完成结果、待处理状态和原有额度由评分节点进入图检查点，后续恢复仅处理缺项。

生产评分器在回调失败时停止新工作；图回调把实际缓存写故障向评分器显式报告。若已完成输出缺少合法的精确请求契约，或不满足当前证据引用校验，图同样不把无写入的缓存当成成功，而是标记 `cacheContractUnavailable` 并先形成检查点。精确请求契约不因本次修复而放宽。处理恢复仍经过原任务费用/未知请求门禁，不释放旧预留或重发未知付费请求。

验证分为两层。实际 `LeadQualificationAgent` 单元测试覆盖：首批已完成后缓存故障导致后批零请求；同批有效项保存失败后缺项修复零请求；缺少可复用合同的备用输出同样停后批；并发2时已在途请求允许完成、第三批不启动。图测试验证完整评分与 `retry-required` 同在检查点、`scoringIncomplete=1`、无结果保存，授权恢复只评分缺失公司。隔离的 [`scripts/verify-assessment-batch-stop-recovery.ts`](../scripts/verify-assessment-batch-stop-recovery.ts) 使用生产图、序列化和真实 PostgreSQL checkpointer，三个独立进程验证读写状态：失败进程2输入/1完成/1待恢复，恢复进程只处理后者，已完成项重评0、13合成额度保留；最终删除测试 thread。该脚本的评分与保存适配器为合成，实际评分器的停止语义由单元测试证明，不把两者合称真实模型端到端验收。

回归：917测试/198文件、typecheck、生产构建、lint 0错误/11既有警告、生产依赖高危审计0；跨进程脚本通过。真实模型、搜索、邮件、API-credit 和现金调用均为0。合成输入2家公司，首轮有效评分1/待恢复1，下轮只使用缺项1，最终有效2/2、图下游使用2/2；缓存写故障1次、模型重试0、有效输出丢弃0，真实 token、延迟、成本节省和用户采用未知。优化机会是将单次付费响应与持久检查点的窗口进一步缩小；若首批缓存和检查点都不可写，本机制只能依赖保守的未知付费重放门禁，不能凭空恢复未持久化输出。真实供应商账单和完整业务闭环仍待验收。
