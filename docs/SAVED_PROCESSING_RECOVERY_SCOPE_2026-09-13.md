# 已保存部分结果的恢复范围准备

阶段80实现确定性准备函数 `planSavedProcessingRecovery`，尚未接入生产入口。它用于后续关联恢复任务，不能代替创建、用户确认、预算核验及实际执行。

已实现并验证：

- 原结果与checkpoint的国家、目标、run/thread一致，停止原因明确为处理未完成或角色待定，保存数量有效且仍有缺口。
- 调用方必须提供数据库实际selected公司身份；唯一公司数与accepted不相符时拒绝，不反推、不拿重复公司填数。
- 缺失校正、缺失评分和角色冲突分别进入准备范围；完整评分、范围外的正常角色和已保存公司不补量。冲突角色保留全部原候选来源，同一域名仅计一个恢复公司；不在此函数中作新角色判断。
- 保留完整校正结果、原证据和原计划范围；只将目标改为原缺口。返回值深拷贝，准备后续输入不修改原状态。重叠candidate ID拒绝。
- 原任务限额减已占用得到可继承上限；0与无单独任务限额分别表示，精确整数计算，不释放原费用。不允许新公司发现。

5项确定性测试、typecheck、局部lint通过。首次测试发现域名归一化函数要求URL，已补对裸域名的转换；类型检查发现项目低于ES2020目标，改用项目一致的BigInt构造形式后通过。全量851测试/生产构建沿用阶段79；本函数尚无生产调用者，0数据库写入、搜索、模型、发信和真实费用。

下一接线要求（未实现，不是验收通过证据）：

1. 从当前用户已完成任务和唯一checkpoint读取原始状态，对照数据库实际选择与原结果，保存来源版本；不能使用浏览器提交的候选或额度作为事实。
2. 事务建立关联恢复任务并保留原运行/回执，幂等返回同一提案。用户确认前不执行付费。与现有“续搜”明确区分。
3. 每次预留重新检查原任务及关联恢复的累计占用、原任务限额和用户累计限额；本函数的剩余额度只是准备值，不能替代并发门禁。原任务未知费用仍必须先核销。
4. 原证据日期/来源保持，不把复制到新run当作新取证；需要重新验证时走已授权证据流程和缓存依赖校验。缺失评分公司已有完整校正在有效依赖下复用；角色冲突须保留来源后重新判断，不凭数量改类。
5. 只处理准备范围，完成后保存新运行并展示原任务与恢复任务的关系，跨任务去重对账；原评分/费用/回执不覆盖。
