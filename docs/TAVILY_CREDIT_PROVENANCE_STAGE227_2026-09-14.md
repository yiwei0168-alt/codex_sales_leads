# Stage 227 — Tavily API-credit provenance in evidence telemetry

The evidence and correction stages previously returned one `creditsUsed` number even when Tavily omitted `usage.credits`. The provider then substituted a pricing-rule estimate, so downstream telemetry could not tell a reported API-credit count from an estimate. This is a credit-observation issue, separate from the USD reservation, provider cash report and invoice ledgers.

The Tavily adapter now emits `creditSource` and nullable `reportedCredits` on Search and Extract responses. A nonnegative safe integer from `usage.credits`, including zero, is a provider credit observation. Missing or malformed usage remains **unreported**; the existing basic/advanced Search or successful-URL Extract rule still supplies the compatibility `creditsUsed` estimate. An empty Extract request records `no-call`. No request body, endpoint, model, route, fee contract, dollar settlement or paid admission rule changed. In particular, the Search request still does not opt in to `include_usage`, because doing so would change its confirmed exact paid request contract.

Evidence and correction stage metrics now separately record reported-credit calls/credits, estimated-credit calls/credits, and HTTP attempts without a matching credit observation. The aggregate `paidSearchCredits` remains the existing mixed operational estimate for compatibility; it is **not** a confirmed provider report or a USD invoice. Failed or retried attempts are not silently counted as reported zero. Historical rows are untouched and cannot be reclassified from absent response data.

Mocked provider tests cover reported zero, omitted/malformed usage, Extract report/estimate/no-call and the unchanged exact number of HTTP calls. The evidence test covers one reported call, one estimated call and a retry of unknown credit outcome; the product graph test confirms the split reaches persisted stage-metric metadata. Full regression: 1,048 tests in 208 files; TypeScript, changed-file lint and production build pass. The generated end-to-end workflow refreshed four affected source fingerprints and its subsequent `--check` passes; workflow version and policy content are unchanged. No real Tavily call, customer job, paid token, API credit, USD spend or email was triggered. The current budget remains the last verified USD12.324404/30, subject to fresh read-only preflight before any future paid run. A03 still lacks other providers' trusted dollar reports and first live matching; A11 still has no whole-run upper bound.

Official interpretation: [Tavily Search response and `include_usage`](https://docs.tavily.com/documentation/api-reference/endpoint/search), [Tavily Extract response](https://docs.tavily.com/documentation/api-reference/endpoint/extract), [API-credit rules](https://docs.tavily.com/documentation/api-credits). API credits are usage units; this change does not treat them as an account-specific USD bill.

Efficiency: two provider response shapes and two workflow stages were inspected; three new tests produced three valid no-paid provenance observations, all used in local acceptance, with zero customer candidates or qualified/downstream adopted leads. The full test run took about 20 seconds and the production build about 25 seconds; real provider latency, real credit reporting coverage, actual adoption and live dollar billing remain unknown. One mocked retry outcome is deliberately retained as unknown rather than discarded as zero. Opportunity: when an exact Search billing-contract change is separately approved, consider opt-in usage reporting and preserve its request identity; until then, compare estimates against a verified account invoice before cash reconciliation.
