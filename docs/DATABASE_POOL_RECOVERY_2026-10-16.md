# PostgreSQL 连接池断线恢复（G01，2026-10-16）

## 已复现的问题

在一次性 PostgreSQL/pgvector 中，先通过真实应用 DAL 取得并释放连接，再由同集群管理员终止该应用后端。修复前子进程在 `pg-pool` 的空闲连接 `error` 事件处退出，SQLSTATE 为 `57P01`。本地 `pg-pool/README.md` 及其 `makeIdleListener` 实现确认该事件须由应用处理，驱动已将坏空闲连接移出池。

该实验复现了确定的进程退出缺陷。此前一次恢复验证的完整错误头部丢失，不能证明该缺陷是原事件的唯一根因。

## 当前行为

- 连接池处理空闲连接错误，保留原池，由驱动移除坏连接。只记录固定日志文字和合规 SQLSTATE，不打印客户端、SQL、URL或错误正文。
- 连接失效会清除安全验证缓存；下一操作重新建立连接并执行角色/TLS 校验。
- DAL 借出连接期间持有临时错误监听，异步断线后不得提交。释放前移除监听，坏连接销毁。
- 回滚失败不覆盖原始操作错误；失败事务的回调不自动重跑，避免重复写入或把未知提交结果当作可安全重试。

## 验证

5 项单元测试及类型/lint 通过。`node scripts/run-tsx.cjs scripts/verify-ma24-fresh-pilot-new-cluster.ts --pool-recovery` 在全新一次性集群中验证：

1. 空闲连接被终止后进程存活，新连接 PID 不同且当前角色仍为应用角色。
2. 借出连接等待期间、SQL 执行期间分别被终止，原始 `57P01` 保留，回调各执行一次，事务内写入均未落库。
3. 下一笔明确的新事务只提交一次。
4. 两个租户作用域分别注入，事务外不保留前一租户值。

前置角色初始化、重复初始化拒绝及原有合成用户/公司隔离和恢复检查也通过。仅迁移至 135，未调用模型，临时容器已清理。
