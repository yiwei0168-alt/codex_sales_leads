# Stage 124: workspace audit-event tenant isolation

`workspace_audit_event.changes` can contain private contact, strategy and mail metadata. The application role previously had table-wide read and write privileges without RLS. Migration 062 enables and forces RLS by owning workspace. It permits an insert or update only when `actor_user_id` is the current application user and the workspace belongs to that user. `updateWorkspaceMode` now uses `tenantTransaction(userId, ...)` to set that context before its workspace update and audit insert. Existing audit events were not rewritten.

The isolated PostgreSQL verifier created two disabled fixture users/workspaces and called the actual `updateWorkspaceMode` product function for each. It read the first user's saved event as the owner; the second user saw zero rows and updated zero rows for that event. A cross-workspace insert and a same-workspace insert impersonating the other user were both denied by RLS. The verifier reported one owner event, zero actual paid calls and 105 ms to final assertion. Fixture rows were removed. The catalog audit's owner-keyed application-readable tables without RLS fell from four to three: `app_session`, `market_workspace`, and `workspace_company`. The catalog filter is narrower than all private-data access paths. Session bootstrap and workspace joins require separate migrations; A13 and overall acceptance remain incomplete.
