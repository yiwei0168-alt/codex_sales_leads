# 工作流用量聚合验收（阶段97）

`GET /api/tasks/usage` 原有操作表 `stages` 和 HTTP 预留表 `billingStages` 保持兼容；新增独立的 `workflowStageMetrics` 与 `workflowModelUsage`。前者按阶段汇总输入/输出项、生成/有效/下游使用、搜索额度和阶段耗时，并仅在逐行计数有效且有生成项时给出下游利用率；后者汇总已记录的模型 token、调用记录、回退和耗时。四类账本存在重叠，不能跨表相加为总花费或总产出。`userAdoptionCoverage="unknown"` 明确表示服务器保存/下游使用不证明用户采用；缺失费用、历史未接入调用继续未知。

实际 API 仍要求鉴权，四个只读查询均以同一用户 ID 和最近30天为范围，并发读取、私有 `no-store` 响应；任一查询失败返回503，不用部分数据冒充完整统计。输出是聚合计数及内部阶段名，不包含原始证据、邮件或私人内容。原产品费用门禁和事件写入不变；无数据库迁移。

验证：路由单测覆盖鉴权、四账本响应、未知费用/采用和失败分支；隔离 PostgreSQL 事务插入同阶段两条合成阶段记录与一条模型用量，核对输入3、生成3、有效2、下游使用2、利用率2/3及模型15 token。另插入计数异常记录，异常数为1且利用率为 null；切换其他用户后查询不可见。全部 fixture 回滚；896项测试/196文件、生产构建含类型检查、改动文件 lint、生成工作流文档检查通过。真实供应商调用、token/API credits 和费用均为0。此验证覆盖 API 到 SQL 聚合契约，**不证明用户实际查看页面或真实业务产生新的阶段记录**。

效率影响：每次调用由两个只读聚合查询增为四个，独立查询并发执行；没有可归因的真实延迟或节省样本。后续应以生产请求延迟监控决定是否需要索引或缓存，不能预先把额外读负载宣称免费。若需回滚，移除新增响应字段与两个查询即可，原字段继续可用。
