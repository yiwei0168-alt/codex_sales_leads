# Stage 125: workspace-company membership isolation

`workspace_company` stores account tier, priority and membership between a global company and a user's workspace. The application role previously had unrestricted table reads and writes. Migration 063 enables and forces RLS through the owning `market_workspace`. The old Mexico discovery and live-lead reporting scripts now set their resolved workspace owner's tenant context. The rolled-back contact-verification publication probe now selects the explicitly resolved target workspace and uses `tenantTransaction`; it no longer selects the first active global workspace. Existing company records, country states and scores were not rewritten.

The isolated PostgreSQL verifier created two disabled fixture users and used the actual `addManualCompany` product function to add one company to each workspace. Each owner saw one membership. The second user read and updated zero rows from the first workspace; a cross-workspace insert was denied. The verifier reported zero actual paid calls and 114 ms to final assertion; both fixture workspaces, memberships and synthetic global companies were removed. The separate `verify-contact-verification-production.ts` passed against the actual product schema, rolled back its synthetic publication transaction and kept no company, email or decision. No model or provider request is made by either verifier.

The catalog audit's narrower set of owner-keyed, application-readable tables without RLS fell from three to two: `app_session` and `market_workspace`. This count does not certify every private data path. Both remaining tables need identity/bootstrap and caller analysis before migration. A13 and overall acceptance remain incomplete.

`npm.cmd run db:migrate` applied migrations 001–063 and checkpoint setup twice on the local acceptance database. Full Vitest passed 969/969 tests in 203 files, typecheck and production build passed, full lint reported zero errors and 11 existing warnings, and production dependency audit found zero vulnerabilities. An isolated-account local production run at `localhost:3022` passed 66 Chrome desktop/mobile checks, including manual company creation, task feed, country switch, contact and cost projections. It removed the fixture and reported zero paid calls and zero real mail sends. The production server was stopped. These are synthetic and rolled-back checks, not the A11 live qualified-lead and trusted-billing loop.

Input volume: two synthetic companies, two manual additions and one separate rolled-back contact publication. Valid memberships saved in the isolated verifier: two; downstream internal reads: two owner memberships and the product UI's 66 regression checks. User adoption remains unknown. Model tokens, search API credits, actual cash, provider calls, paid retries and SMTP sends were zero. Foreign read/update output was correctly zero and the cross-tenant insert was rejected; no valid company output was discarded. The verifier took 114 ms including SQL setup, with per-stage and browser latency not separated. Internal membership utilization was 2/2; actual user adoption efficiency is unknown. The optimization opportunity is to reuse tenant-scoped membership and stored company evidence while hardening the remaining workspace/session bootstrap tables, rather than repeat paid search or contact lookup.

Rollback would remove the policy and RLS flags in a controlled migration. Tenant-scoped callers can remain; removing RLS would reopen cross-user membership reads and is an emergency compatibility path only.
