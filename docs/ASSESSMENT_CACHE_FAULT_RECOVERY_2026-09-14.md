# 阶段105：评分缓存故障的跨进程恢复验收

结论：在隔离的合成评分任务中，评分缓存读取故障发生在评分调用前，任务保留原检查点；读取恢复后恰好评分一次。可选缓存写入故障不丢弃这次完整评分，真实 PostgreSQL 图检查点保留结果；另一个进程恢复后直接做复核和保存，评分不重跑，原有 13 合成额度不清零。没有调用模型、搜索供应商、邮件或真实业务保存。

验证脚本 [`scripts/verify-assessment-cache-fault-recovery.ts`](../scripts/verify-assessment-cache-fault-recovery.ts) 使用生产图、生产序列化和 PostgreSQL `PostgresSaver`，在四个独立 Node 进程中顺序执行 `seed → read-failure → write-failure → resume`，最终删除隔离 thread。业务适配器完全合成。实测调用计数：读取故障进程缓存读1、评分0；写入故障进程缓存读1、缓存写1、评分1；恢复进程缓存读0、缓存写0、评分0、复核1、保存1。写入故障后的 `cachePersistenceFailed=true` 与已完成 assessment 同在检查点，额度始终13。

本项只验证**完整评分节点已返回并写入图检查点**的故障边界。若某一批次已得到付费响应、缓存写失败，随后同一个评分节点在图检查点形成前中断，本证据不能证明该批单项输出已持久保存；未知付费请求仍须由现有重放门禁保持暂停，不能自动再发。缓存 SQL 本身的用户/国家隔离另有既有测试，本脚本注入的是适配器故障，不模拟数据库全局停机。真实模型输出、服务商账单、用户采用和整条业务闭环仍未验收。

回归：脚本四进程通过；`npm run typecheck`、`npm test`（911项/198文件）、`npm run build`、`npm run lint`（0错误、11既有警告）通过。脚本只创建并清理自己的检查点；真实费用和 API 用量均为0。效率口径：合成输入1家公司，有效评分输出1，下游复核/保存各使用1，节点级已完成输出利用率1/1；缓存读失败1、写失败1、模型重试0、输出丢弃0，真实模型 token/API credits、真实延迟、真实节省与用户采用未知。优化机会是将批内已完成输出的持久性与未知请求门禁作为后续单独验收项。
