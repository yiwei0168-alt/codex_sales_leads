# Gemini grounding usage provenance — stage 183 (2026-09-14)

The product previously counted distinct `google_search_call` queries from response steps and returned zero when the steps were absent. The [official Interactions API](https://ai.google.dev/api/interactions-api-v1) exposes `usage.grounding_tool_count` with a `google_search` count. The [official grounding guide](https://ai.google.dev/gemini-api/docs/google-search) says Gemini 3 search is billed per nonempty unique query. A missing step list therefore cannot prove zero billable searches.

The discovery provider now uses a valid server-reported Google Search count first. When it is absent or malformed, it derives the distinct nonempty query count from complete `google_search_call` steps. When neither source is complete, the count remains **unknown** (`groundingQueries` omitted), and the telemetry records the source as `unknown`; the hybrid executor preserves that omission on completed or failed Gemini calls. Cache hits and skipped routes still represent zero new Google searches. This is an additive telemetry contract; no past events are rewritten.

Three synthetic completed responses verified reported count 3 versus one visible step, fallback count 1 for duplicate/empty queries, and absent count remaining unknown. Product executor fixtures verified that completed and failed Gemini requests do not convert an unreported count to zero. The full regression passed 1,021/1,021 across 207 files, typecheck, changed-file lint and production build passed. All transports were local mocks: real model/search calls, tokens, paid API credits, cash and retries were zero. Focused tests took about 1.3 seconds, full tests about 17 seconds and build about 24 seconds; real provider latency and customer adoption remain unknown. The missing count is a telemetry gap, not a discarded candidate.

This improves post-response reconciliation only. It does **not** supply a pre-request maximum for model-initiated Google searches, activate the held Gemini tariff, change search routing, or establish a whole-run A11 cost bound. The optimization opportunity is to combine provider-reported usage with a future officially enforceable per-request tool limit or keep this route held; post hoc usage cannot fund a conservative reservation before transmission.
