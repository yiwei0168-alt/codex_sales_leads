# 恢复提案的原子保存与复用（阶段83）

在阶段82来源核验基础上，`proposeProcessingRecovery` 将子任务、来源证明/限定公司范围、恢复关联、回执和聚合审计放入同一数据库事务。用户预算锁与原任务锁串行化重复请求；重复请求返回同一子任务，不重复回执或保存量。提案后来源检查点变化时拒绝自动替换，保留原提案核对。原结果、原账单和检查点不重写。

恢复子任务使用原国家与具体角色、原缺口数量，并通过055关联继续受到祖先预算限制。生产执行器在任何普通工作流初始化前检查恢复关联，专用缺项执行路径未接通时拒绝普通搜索。未开放HTTP/页面入口，也未将提案标为用户已确认或执行成功。这是接线过程的临时保护，不能作为最终恢复功能完成证据。

验证：全量867测试/190文件、生产构建、局部lint通过。扩展真实PostgreSQL与生产检查点脚本 `verify-saved-recovery-source.ts`：事务强制中断后无子任务/关联；两次并发提案仅一个子任务/回执，审计保存总量为1、用户采用unknown；来源变动拒绝；实际生产执行器拒绝恢复子任务走普通发现。fixture及检查点清理，供应商调用/真实费用/发信为0，1微美元仅合成预留。

效率观测：每次准备输入1，首次生成/有效/保存1、重复0；下游使用0、用户采用null；token/API额度及费用0，真实毫秒延迟记录，重试0，重复丢弃原因计1，首次利用率1/重复null。这里利用率指有效提案产出，不代表用户采用或最终公司合格率。后续复用有效证据和已完成单项仍需专用执行器核验依赖，不能将复制时间当证据更新。

剩余：接专用恢复确认/执行，原范围公司补证有效期、冲突角色及单项缓存依赖；新运行与原运行的结果关联；最终页面与真实业务验收。普通UI54组沿用阶段81，没有新页面验收。整体验收未完成，S01仍待用户确认。
