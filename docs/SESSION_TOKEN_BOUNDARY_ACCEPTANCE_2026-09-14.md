# Stage 127: session-token boundary under RLS

`app_session` must be queried by a secret token before a user identity is known. Migration 065 enables forced RLS with an owner-only insert policy and removes direct application-role SELECT, UPDATE and DELETE privileges. `createSession` inserts with the authenticated user's tenant context. `getSession` and `deleteSession` call two narrow `SECURITY DEFINER` functions by SHA-256 token hash: the first updates last-seen and returns identity only for an unexpired session whose user is active; the second revokes that token. Both functions set `search_path` to `pg_catalog`, reference tables explicitly and grant execution only to the application role. The migration checks that its owner role bypasses forced RLS; the local migration role is `postgres` with superuser and BYPASSRLS capability. Deployment under a different migration role must satisfy that same requirement or migration 065 stops. Existing sessions were not rewritten or invalidated.

The isolated SQL verifier inserted one owned active and one expired session and refused a second user's forged insert. Direct application-role SELECT, UPDATE and DELETE were denied. The token function resolved the active session, rejected expired and missing hashes, rejected the same token while its user was disabled, and returned no row after revoke. A production HTTP probe on `localhost:3024` passed five checks: anonymous session, login, authenticated session, logout and anonymous session after logout. The browser-wide local production run passed 66 Chrome desktop/mobile checks including real login and disabled-user denial. Fixtures, sessions and server were removed; actual paid calls and real mail sends were zero.

`npm.cmd run db:migrate` applied migrations 001–065 and checkpoint setup repeatedly, including after the role precondition was added; the SQL verifier passed again after replay. Full Vitest passed 969/969 tests in 203 files, typecheck and production build passed, full lint reported zero errors and 11 existing warnings, and production dependency audit found zero vulnerabilities. The read-only catalog filter now reports zero owner-keyed application-readable public tables lacking RLS out of 76 public tables. This filter does not inspect every unkeyed table, function, schema, endpoint, private content path or real business record, so A13 and overall acceptance are not declared complete. A11's real natural-language-to-qualified-company and provider-billing loop remains unverified.

Input volume: two synthetic session hashes, one owned active row, one expired row and one real-HTTP fixture login/logout. Valid internal identity output was one active resolution and one authenticated HTTP session read; the logout removed that credential from downstream use. Real user adoption is unknown. Model tokens, search API credits, actual provider calls, actual cash, paid retries and SMTP sends were zero. Expired, disabled, absent and revoked tokens were discarded for explicit auth reasons; none counted as a business rejection. SQL verification took 132 ms on the initial run and 474 ms with five HTTP checks; subsequent replay checks were 204–216 ms. Browser per-stage latency was not separated. Internal valid-token utilization was 1/1 before logout, with user adoption efficiency unknown. The optimization opportunity is to keep token lookup in the narrow indexed database functions and avoid application-side session enumeration or any paid dependency in authentication.

Rollback must restore prior session callers and table privileges together with removing the functions/policy/RLS in a controlled migration. That would reopen direct application-role session access and is an emergency compatibility path only. A safer recovery is to correct the migration-role capability or function deployment while retaining RLS.
