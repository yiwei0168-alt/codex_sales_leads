# 阶段109：评分响应已记账但结果未落盘时的恢复门禁

阶段106已在评分批次缓存写失败后停止尚未开始的付费批次，并把已完成项写入图检查点；仍有一个更窄的故障窗：供应商响应已返回、`paid_call_reservation` 已结算，但缓存和评分节点检查点都没有保存输出。原恢复门禁只拦截在途、超界及未核销的未知费用。已报告的成功响应可以穿过该门禁；若修复批次变化，精确 HTTP 指纹也不能识别同一家公司刚买过的丢失输出。

现在生产恢复在重入 `score_candidates` 前保留**原始持久检查点时间**，且重复恢复不刷新该时间。评分节点先加载已完成检查点项和当前有效缓存，再只对真正缺失的公司查询同一用户、同一任务、检查点之后的评分付费账本。若账本表明相关公司已有成功或输出不完整的 `lead-qualification` 响应，或旧账本的评分阶段响应缺少模型任务标记/可核实的公司归属，则在新模型调用前报 `paid-request-already-recorded`。其他公司、旧检查点之前的历史请求、非评分请求不触发此门禁。仅使用已有公司/国家哈希、模型任务和响应状态；不保存提示、证据、凭据或邮件原文。有效缓存仍可复用，原预留及报告费用不释放。处理方式是保留任务待核查，不能从账本重建丢失的语义评分，也不自动判公司不合格。

验证：新增账本作用域和图恢复单测；`scripts/verify-uncheckpointed-score-guard.ts` 使用隔离账号、真实 PostgreSQL 付费账本和 LangGraph checkpointer，在独立进程先写预评分检查点，再写一笔**合成**评分预留7 micro-USD、已报告5 micro-USD的成功响应，下一进程两次调用生产 `runLeadWorkflow` 均在再次评分前被拦下。任务原始时间屏障保留；其他公司及其他用户不受影响；账本始终只有1笔、合成占用保持7 micro-USD，真实模型/搜索/邮件请求均为0，fixture和 thread 清理。956项测试/202文件、typecheck、生产build和全库lint通过（0错误、11项既有警告）。该合成金额不计入真实用户 USD30 验收占用。

遥测口径：合成输入公司1、有效付费响应账本1、可恢复评分输出0、下游使用0、重放阻止2；模拟 token 输入/输出各1，真实 token/API-credit/现金增量0，合成报告5、预留及占用7 micro-USD；调用延迟模拟1 ms，端到端跨进程耗时由脚本运行记录而非产品实测。丢弃原因为 `paid-response-output-not-durable`，利用率为0/1，用户实际采用未知。优化机会是让单次响应与持久输出形成更小的原子边界；当前安全策略优先阻止重复付费。该验证不证明真实供应商账单匹配、实际模型输出正确或完整真实业务闭环，A06/A11仍未全通过。
