# 邮箱 DNS 故障排查与应用层绕行（2026-11-03）

关联 `MAIL-AUTO-SYNC-01` 的连续运行证据。三条历史任务记录的直接错误为系统域名解析 `ENOTFOUND`，已按原日期补齐；不能据此判定邮件服务商故障或永久根因。

## 本轮实测

当前 Windows 与 Node 系统解析均可返回公开邮件服务器的公网地址。对应日期的系统日志中未找到该域名的 DNS 事件；日志缺失不能推翻任务中的错误记录，也不足以解释历史原因。应用原配置为 `MAILBOX_DNS_MODE=system`。

独立诊断进程分别调用产品现有系统解析及 `alidns-doh` 分支，均成功。随后用既有授权连接执行 HTTPS DNS 路径下的只读 IMAP 凭据验证，通过原有 TLS 证书与服务器名称检查。没有读取邮件正文、发送邮件、创建同步或调用模型；凭据仅在内存使用，没有写入日志或证据。

## 已实施

选择产品已有 `alidns-doh` 作为应用邮箱解析方式，只修改忽略的本地环境文件，不提交环境文件。该分支只向固定 HTTPS DNS 地址发送公开服务器域名及记录类型，不携带邮箱地址、应用密码或邮件正文；解析结果继续执行公网地址检查。TLS 校验保持开启，没有修改 Windows DNS、防火墙或网络路由。

确认无活跃任务后，重载相同代码的 Web 和邮箱 Worker，使二者加载同一模式；API、主 Worker、线索和检索组件未重载。新进程从配置读取模式成功，受保护自动同步接口仍为 401；标准启动入口返回 ready 并复用六个现有进程。迁移凭据、付费阶段覆盖及云追踪均未带入运行进程。每日 08:00 设置未变，也未新建同步任务。

这是针对已观察解析故障的应用层替代方案，不是新增自动降级或自动重试策略。HTTPS DNS 路径仍依赖其网络及现有代理可用性。历史根因、未来持续稳定性及下一次 08:00 自然运行结果仍未关闭；后续不得把本轮只读连接通过当作下一次自动同步已完成。

需要恢复原路径时，应先确认无活跃任务，将本地模式恢复为 `system` 并重载对应进程；不需要数据库回滚。本轮未执行该恢复，不将恢复说明当作实际演练。[排查及实施收据](evidence/mailbox-dns-mitigation-2026-11-03.json)。
