# Stage 126: market-workspace tenant isolation

`market_workspace` contains a user's workspace objective, mode and metadata. Migration 064 enables and forces RLS directly on `owner_id`. The product workspace read now uses `tenantQuery(userId, ...)`. Account provisioning sets `app.current_user_id` after the user upsert and before its workspace insert in the same transaction. The operator workspace resolver first selects only active user IDs/emails, then checks each user's workspace under that user's tenant context; it still rejects an ambiguous untargeted selection. Release-profile and read-only acceptance utilities use the same scoped pattern. Existing workspaces and history were not rewritten.

The isolated SQL verifier created two active fixture users/workspaces. The explicit email resolver returned each matching workspace. `getCurrentWorkspace` read the owner's workspace; the actual `updateWorkspaceMode` path changed the first owner's mode to growth. The other user read and updated zero rows from that workspace and could not insert a row owned by the first user. A separate child-process execution of the actual `upsert-app-user.ts` provisioned a random account, whose new global workspace was visible under its tenant; all three fixture users/workspaces were removed. The verifier reported zero actual paid calls and 1,375 ms to final assertion. `verify-ui-contracts.ts` also passed application-role workspace/task reads with temporary writes rolled back and no model/mail calls.

The read-only catalog audit now shows one owner-keyed application-readable table without RLS: `app_session`. That audit is deliberately narrower than a full privacy certification. Session creation and token lookup happen before the requester is known, so this table needs a bootstrap-safe contract rather than the owner policy used for workspaces.
