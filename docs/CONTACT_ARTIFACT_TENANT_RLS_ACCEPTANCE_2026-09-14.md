# Stage 123: contact-artifact tenant isolation

The application role could read owner-keyed contact and verification artifacts without row-level security. Migration 061 enables and forces owner-scoped RLS on `company_enrichment_run`, `company_enrichment_run_item`, `company_web_evidence`, `company_contact`, `company_email_candidate`, `contact_verification_run`, `contact_model_assessment`, `contact_verification_decision`, and `contact_review_queue`. Child-row policies also require the referenced run, email, contact or decision to be visible and, where applicable, to belong to the same workspace and company. Application scripts for enrichment, verification and reporting, plus `/api/contact-enrichment/runs/latest`, now set the authenticated workspace owner's tenant context. No historical contact, assessment or score rows were rewritten.

The read-only catalog audit covered 76 public tables. Its narrower set of owner-keyed, application-readable tables lacking RLS fell from 12 to 4: `app_session`, `market_workspace`, `workspace_audit_event`, and `workspace_company`. This is not a proof that every private table is protected. Existing evidence/run, assessment/email and decision/email workspace mismatches, and workspace-null quarantined emails, were each counted as zero in this local database. These counts are not a substitute for a production-data audit. The four remaining tables require a separate auth and workspace-caller migration; this stage does not mark A13 or overall acceptance complete.

`node scripts/run-tsx.cjs scripts/verify-contact-tenant-rls.ts` created two disabled fixture users and two workspaces. The actual `lookupAndStoreContacts` code persisted one synthetic run, item, evidence, contact and email through a fake zero-credit provider, then reused the cache on the second call. Verification run, assessment, decision and review rows were inserted under the application role. The owner saw all nine table rows; the second user read and updated zero rows in each, could not insert a run for the first workspace, and could insert one for its own workspace. The verifier reported one fake provider call, zero provider credits, zero actual paid calls and 263 ms to its final assertion. All fixture rows were removed.

`npm.cmd run db:migrate` applied migrations 001–061 and LangGraph checkpoint setup twice successfully. Full Vitest passed 969/969 tests in 203 files, typecheck and production build passed, and targeted ESLint reported zero errors. A separate local production server on `localhost:3020` passed `verify-authenticated-ui.ts`: 66 checks across Chrome 1366 px desktop and 390 px mobile, including real HTTP and SQL reads for task, budget, country, memory, manual company, strategy, pause and usage views. The browser script removed its fixture and reported zero paid calls and zero real mail sends. It is a broad product regression, not a dedicated contact-run HTTP assertion; that endpoint still needs a targeted authenticated response check in a later stage. The server was stopped after verification.

This stage used one synthetic company, one generated contact and email, one fake provider result, one cache reuse, and one synthetic verification chain. Valid internal artifacts and downstream test reads were one each; qualified sales leads and user adoption were not measured. Model tokens, search API credits, actual cash cost, external requests, paid retries and SMTP sends were zero. Per-request provider latency is inapplicable; the 263 ms verifier duration includes SQL and cache checks, while browser check latency was not split by stage. No outputs were discarded; legacy workspace-null email rows would remain hidden if encountered. The efficiency opportunity is to keep completed contact evidence in owner-scoped cache and to migrate the four remaining owner-keyed tables with their auth/workspace call paths, without paying to rediscover or reconstruct stored results.

Rollback must remove the nine policies and RLS flags in a controlled migration together with restoring the former unscoped callers. Such a rollback would reopen cross-user access, so it is an emergency compatibility path rather than an acceptable steady state. Historical data do not need reverse rewriting.
