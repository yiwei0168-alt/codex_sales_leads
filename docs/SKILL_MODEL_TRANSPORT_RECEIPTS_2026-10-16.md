# G09 model transport receipts — implementation stage

This stage adds an internal collector request factory and a verifier for successful model transport receipts. It does not qualify a production runner, enable a Skill, or close G09.

## Protocol and workflow

- Trust registry keys have explicit `runner-declaration` and/or `model-transport` purposes. Existing entries default to declaration only. A transport key cannot sign a runner declaration unless separately enrolled for that purpose.
- The configured factory requires a controlled production process, an enrolled Ed25519 signing key and the official OpenRouter HTTPS endpoint. It accepts no caller transport or signing key. Model calls retain the existing paid-call admission boundary.
- The factory explicitly requires an owned `SpendContext` with a UUID operation and nonempty stage, and pins its full digest. It rechecks before invocation, at the actual guarded transport boundary and after model completion. This closes the unscoped CLI bypass in shared `budgetedFetch` for this collector; the shared behavior for other CLI callers is unchanged. A spend scope is an engineering billing boundary, not user authorization to run new paid evaluations.
- Each successful receipt binds owner, freeze, evaluation, arm, plan, snapshot, step, route, collector and deployment to the exact request manifest and parsed response semantics. Authentication headers and private keys are not included.
- Response hashing normalizes only tool-call IDs, which the durable journal adapter replaces. Text, function names, arguments, ordering and reasoning remain bound. This is a semantic response receipt, not a raw wire-response signature.
- The request factory observes the actual response status and only signs HTTP 200 results. The journal verifier loads server-side records, requires pending-production source classification and all-successful attempts, validates signed times inside persisted attempt times, rejects reused generation IDs and rechecks records and registry after verification.
- Registry revocation is reloaded on each check. No source classification is promoted by these functions; `automaticActivation` remains false and journal verification reports `binaryVerified: false`.

## Evidence and remaining work

The locked policy adapter now uses `withBoundTenantTransaction` so its nested tenant readers share the caller's connection and transaction. This fixes the self-wait risk from taking a new connection's Skill share lock while the outer connection holds an update lock. The scope validates database role, account, application role and transaction ID before/after work; nested ownership/explicit-role switches and unscoped transaction calls reject. A two-query transaction ID check rejects autocommit clients before callback execution, and an active-scope guard rejects escaped async descendants after completion. Outside this explicit internal scope, ordinary database behavior remains unchanged. Existing notes about policy identity preparation using separate tenant transactions are superseded for this bound path. Full per-case material revalidation is still the next missing connection; this scope alone does not prove production provenance or authorize activation.

`evaluateLockedSkillAcceptancePolicy` retains the caller's evidence locks while deriving all original run references from the stored bundle, rebuilding each distinct source's execution identity with the existing server reader, re-reading the locked artifact/latest judgments/current pin, and applying the real policy with a database clock timestamp. Signed retryable failures are now implemented with `skill-model-transport-failure-v1`. The controlled factory binds an observed request manifest, failure reason, observed HTTP status (or null), owner/freeze/arm/step/route and times, retaining the original error for existing fallback classification. Only allowlisted retryable failures with consistent observations, active trust/freeze and unchanged spend context are signed; cancellation or failed signing checks leave no certified failure. Internal error metadata is copied into the unavailable journal outcome before advancing. The server verifies every predecessor signature, exact request/route/tool binding, database attempt times and trust, in addition to the pre-existing complete fallback-chain check and selected success receipt. Unsigned predecessors reject the transport audit. This supersedes earlier success-only verifier limitations. Terminal/unknown/cancelled runs remain unqualified; timeout receipts do not prove provider completion or absence of charges.
