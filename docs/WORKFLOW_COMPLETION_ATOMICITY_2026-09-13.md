# 任务完成与回执的事务一致性

阶段78补齐 A06/A12 的中断边界：旧执行器分三次事务更新 job、action、会话回执，中间失败会留下不一致状态。现在完成写入在同一租户事务中，按 action→job 顺序锁定，并核对用户、会话、action 和 graph thread。

并发或重复完成复用同一 graph thread 的一致回执；业务结果或既有回执冲突时保留原记录并拒绝覆盖。也识别缺少新 completionJobId 标记的历史回执，不改其原观测、不删除历史重复数据。失败/暂停的任务与动作状态同样在一个事务内写入，已完成任务忽略迟到失败，避免提交确认丢失后被降级。

新回执仅记录必要内部关联与聚合：输入/生成/有效/保存各1，模型token/API/费用0；下游阅读采用、完整重试次数与利用率未知。latencyMs是该次成功事务写入回执前耗时，不是提交后总延迟；失败事务不被虚构为零耗时成功。没有发送邮件、通知外部联系人或启动额外搜索。

- `scripts/verify-production-recovery-guard.ts`：真实应用SQL事务在完成写入后注入回滚，job/action仍为failed，完成回执0；2次并发完成后回执1；迟到失败后job全部选定字段不变；冲突结果和错误用户/thread/会话拒绝。回执观察保存1、下游采用unknown、费用0。
- 原reserved/unknown/重复unknown三个实际入队、认领、执行器门禁仍通过，原checkpoint完整保留、7微美元合成预留不变。完成业务结果为合成输入，不证明真实线索业务已执行。
- 全量849 tests/187 files、生产build含类型检查、改动文件lint通过。数据库fixture清理，0供应商调用/发信。页面回归结果见最新页面报告。

无schema变更。回滚代码不需删除新增回执metadata，但旧版本会恢复分步提交的风险；旧终结缺项合并恢复和最小真实业务闭环仍未完成。
