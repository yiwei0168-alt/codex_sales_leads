# Stage 200 — SearchAPI effective credential in discovery recovery identity

The SearchAPI provider accepts `SEARCHAPI_API_KEY` after trimming, then falls back to the compatibility alias `SearchApi.io_API_KEY` when the standard value is blank. The persisted discovery-session dependency previously hashed the raw standard environment value with nullish coalescing. Under a whitespace-only standard key, an alias account change could alter the actual paid request while leaving the dependency hash unchanged, permitting completed search work from the prior account to be reused as if its request contract were the same.

The provider and recovery dependency now use one effective connection resolver for the selected API key and base URL. The resolver returns credentials only in process; the checkpoint persists only the outer SHA-256 dependency digest. A changed effective alias invalidates the old paid checkpoint. Equivalent blank standard values produce the same digest. Existing checkpoints created under the affected blank-standard-key configuration may intentionally fail to resume automatically and require review of purchased work; there is no automatic replay or historical rewrite. Normal nonblank standard configuration retains the same effective identity. No key value is logged or added to documentation, and no provider, tariff, search scope, role or score policy changed.
