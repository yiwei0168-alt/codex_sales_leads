# v1.6 评分治理与下游交接报告设计

## 结论

评分链路应该引入多 Agent，但只对高风险样本进行**盲独立复评和裁决**，不应让多个 Agent 全量自由讨论，也不应简单采用多数投票。推荐流程是：

`结构化事实账本 → 主评分 Agent → 确定性异常路由 → 盲独立复评 Agent → 分歧裁决 Agent → 最多一次定向补证`

补证 Agent 和打分 Agent 完成后，可以共同为开发策略和开发邮件环节提供一份简短报告，但它们不应再自由协作撰写自然语言总结。更稳妥的做法是增加一个确定性的 `LeadHandoffAssembler`：它只组装、校验证据引用、分离事实和推断、隔离冲突并裁剪长度，不创造新事实。

## 一、证据识别错误和错评为什么会发生

### 1. 证据获取和实体解析错误

- 搜索结果可能指向同名公司、目录页、旧域名或错误官网。官网错误会把另一实体的业务和品牌关系写入候选公司。
- 抓取失败、动态网页、robots 限制和内容截断会造成“未发现证据”。未发现不等于事实为假，特别是库存、采购权、合作品牌和公司规模等公开披露较少的字段。
- 共享补证提高了工具间的可比性，但如果规范实体错误或 dossier 混入无关页面，错误也会被所有工具共享。
- 搜索摘要适合发现候选，不适合作为最终事实。摘要可能截断限定词、拼接不同段落，或已经过搜索引擎改写。

### 2. 补证 Agent 的结构不足

- 当前补证触发条件主要检查身份、基础 networking 和角色，未系统检查产品族、采购、选型、报价、部署、品牌合作等直接影响 Fit 和 Path 的事实。
- 角色由模型结果与确定性正则取并集。正则误命中的角色无法被模型删除，容易产生“只增不减”的角色污染。
- 泛化搜索词同时包含多种角色，若只按域名聚合，可能把目录、招聘、供应商或新闻页面中的角色词误认成候选公司的自有业务。
- 补证结果没有逐项的 `claim → evidenceIds` 账本。下游只能看到一组证据 ID 和一段理由，无法可靠判断某条证据究竟支持身份、角色、产品、品牌关系还是采购影响力。

### 3. 打分逻辑把“不确定”误当成“不通过”

- 历史规则曾把搜索通道错配或角色错配直接变成零分。这衡量的是发现工具的分类准确率，而不是经过产品纠错后交付给用户的线索价值。
- 硬门槛只有 true/false，缺少 `unknown`。模型失败、抓取失败或信息未公开时容易落成 false，进而把真实且有价值的公司错误拒绝。
- 路径评分存在正则封顶；德语同义表达或非模板化描述未命中时，模型已经识别出的采购、选型或实施能力仍可能被压低。
- 评分后的确定性规范化可能改变硬门槛、合作路径或证据 ID，但当前升级复核在规范化之前决定，后生成的严重分歧不会自动触发复核。
- v1.5 回溯评分还存在一个明确实现缺陷：纠错了角色和通道，却继承旧版的 Fit、Path、Confidence 等级。新权重乘在旧结论上，导致真实业务已补全的候选仍维持低分。

### 4. 模型相关错误和评分锚点不足

- 补证和主评分默认使用同一模型家族时，二者容易共享同一种理解偏差；后一环节并不是真正独立验证。
- “产品相关”“合作路径明确”“信息可信”等等级缺少足够多的正反例锚点，模型可能把同一事实分别解释为 2、3 或 4。
- 长尾小公司通常只有官网单一来源。若沿用大型分销商的多源门槛，会系统性低估 Installer、VAR 和本地 Reseller。
- 确定性关键词抽取可审计但仍可能跨段组合无关上下文。例如同一页面分别出现某品牌和“合作伙伴”，并不必然证明两者存在合作关系。

### 5. 持久化和下游引用会放大误差

- 当前持久化逻辑可能把打分理由的第一条复制为每条证据的 claim，造成“页面真实、claim 却不由该页面支持”的语义错配。
- 当前邮件校验主要检查是否存在引用以及引用 ID 是否有效，尚不能保证每一个对外事实句都有对应证据。
- 如果开发策略或邮件 Agent 直接读取混合的事实、推断和评分理由，它可能把内部判断（例如“可能有采购权”）改写成对外确定事实。

## 二、是否应采用多 Agent 讨论或投票

### 决策：选择性独立复评，不采用自由讨论或简单投票

| 方案 | 判断 | 原因 |
|---|---|---|
| 单 Agent 全量评分 | 不足 | 成本最低，但同一提示和模型的系统性偏差无法被发现 |
| 两 Agent 自由讨论 | 不建议 | 后发 Agent 容易被前者锚定，讨论日志长且难复现，事实还可能在对话中漂移 |
| 三 Agent 多数投票 | 不建议作为主机制 | 多数只能降低独立随机误差；同模型、同证据或同提示下的相关错误会形成一致错判 |
| 盲独立复评 + Judge | 推荐 | 第二评分者看相同冻结证据但看不到主评分；Judge 只处理实质分歧，可拒绝双方或请求一次定向补证 |

多 Agent 解决的是**解释和判断的不确定性**，不能修复错误实体、污染证据或继承旧分等确定性缺陷。因此必须先完成实体解析、原子事实账本、unknown 状态和评分实现修复，再引入复评。

### 建议触发复评的条件

仅在以下任一条件出现时调用第二评分 Agent：

- 任一硬门槛失败，或模型判断与确定性事实规则在硬门槛上不一致；
- 总分处于 40–60，或接近 Top 10、推荐/不推荐等产品决策边界；
- 补证置信度低于 75，或主评分置信度低于 70；
- 补证过程中发生官网、实体身份、角色或目标通道变更；
- Fit/Path 很低，但账本存在 Distributor、VAD、在售产品、相邻品牌、采购、选型或安装等反向信号；
- 分数很高，但只有稀疏证据、单一非官网来源或大量 unresolved 字段；
- 非英语页面、角色多义、证据冲突或无官方来源；
- 随机抽取 5%–10% 未触发样本用于监控路由器的漏报。

### 复评和裁决约束

- 主评和复评使用相同的冻结事实账本及其哈希，但使用不同模型家族或至少不同提示结构；二者互不可见。
- 输出必须是逐维度等级、理由、`findingIds/evidenceIds` 和 confidence，而不是只给总分。
- Judge 只看到 A/B 匿名结果、事实账本和差异，不知道工具来源，避免 provider 偏见。
- Judge 可选 `accept_a`、`accept_b`、`merge_dimensions`、`insufficient_evidence` 或 `targeted_research`，不能凭空新增事实。
- 定向补证最多一次，只搜索 Judge 指明的缺口；返回后重新运行发生分歧的维度，不开启无限讨论。

若 20%–30% 样本触发复评，预计评分调用量约为单评的 1.2–1.4 倍，只有真实分歧再增加 Judge；这是设计估算，需用生产 Trace 验证。相比全量双评约 2 倍和三票约 3 倍，更适合当前对质量与成本的共同目标。

## 三、补证与评分如何形成下游关键报告

### 1. 责任边界

- 补证 Agent 负责：实体、公开业务事实、角色可能性、产品族、品牌关系、商业动作以及逐项证据。
- 打分 Agent 负责：基于冻结事实账本独立评价 Fit、Path、Confidence、角色/通道质量以及风险和未知项。
- `LeadHandoffAssembler` 负责：验证引用、处理冲突、事实/推断分离、字段裁剪和生成面向不同下游的视图。
- 开发策略 Agent 负责：结合 Cudy 知识库，把候选事实转为合作假设、切入角度和下一步动作。
- 邮件 Agent 负责：只把允许对外使用且有证据的事实写入邮件；不得直接继承内部评分推断。

### 2. 推荐的结构化交接对象

```ts
interface LeadDevelopmentHandoff {
  version: "lead-handoff-v1";
  provenance: {
    dossierId: string;
    evidenceSnapshotHash: string;
    correctionRunId: string;
    scoringRunId: string;
  };
  identity: {
    companyName: string;
    officialUrl: string | null;
    market: string;
    possibleRoles: string[];
  };
  decision: {
    score: number;
    recommendedRoutes: string[];
    scoreConfidence: number;
    reviewStatus: "primary" | "secondary-confirmed" | "judge-resolved" | "unresolved";
  };
  externallyUsableFacts: Array<{
    factId: string;
    kind: string;
    statement: string;
    evidenceIds: string[];
    sourceTypes: string[];
    confidence: number;
  }>;
  internalInterpretations: Array<{
    interpretationId: string;
    statement: string;
    basedOnFactIds: string[];
    confidence: number;
  }>;
  personalizationHooks: Array<{
    hook: string;
    basedOnFactIds: string[];
    allowedInEmail: boolean;
  }>;
  unknowns: string[];
  risks: string[];
  doNotClaim: string[];
  quality: {
    readyForStrategy: boolean;
    readyForEmail: boolean;
    conflicts: string[];
    warnings: string[];
  };
}
```

建议限制为 4 KB 左右或 600–800 tokens：最多 5 条外部事实、3 条内部推断、2 个个性化切入点、4 个未知项、3 个风险和 6 条核心证据。原始网页摘录不复制进报告，需要时按 evidence ID 获取。

### 3. 给两个下游 Agent 的不同视图

开发策略 Agent 可以读取完整 handoff、评分维度、内部推断、未知项和 Cudy 知识库，以便形成合作路径假设。但策略中的新推断必须标记为 hypothesis，不能回写成候选事实。

开发邮件 Agent 只读取：

- `externallyUsableFacts`；
- `personalizationHooks[allowedInEmail=true]`；
- `doNotClaim`；
- 已批准的开发策略；
- Cudy 公共知识、Steven 的身份记忆和邮件模板规则。

邮件中每个候选公司事实句应使用 `[LEAD:F1]` 形式绑定事实；Cudy 自有事实使用独立的 `[KNOWLEDGE:<id>]`。校验器必须逐句验证引用，而不是只检查整封邮件是否至少存在一条引用。

### 4. 推荐的工作流位置

```text
discover
  → normalize_identity
  → correct_and_collect_evidence
  → freeze_fact_ledger
  → primary_score
  → anomaly_router
      ├─ no review ──────────────────────┐
      └─ blind_secondary → judge → ?research
                                         ↓
  → assemble_handoff_brief
  → persist_candidate_and_handoff
  → build_development_strategy
  → draft_email
  → sentence_level_citation_validation
```

正式实现时，应把当前单节点的“策略＋邮件”拆成两个节点。这样策略 Agent 可以使用内部解释，而邮件 Agent 只能使用经批准的对外事实，减少把评分推断写成客户可见断言的风险。

## 四、实施优先级与验收标准

### 阶段 A：先修确定性问题

1. 为事实增加 `true / false / unknown / conflicting` 状态和原子 `findingIds → evidenceIds` 映射。
2. 将模型/抓取失败标为 retryable 或 unresolved，禁止自动写成 false/0。
3. 修正角色并集、路径正则封顶、评分后不升级以及持久化 claim 复制问题。
4. 确保纠错后的多角色真正重路由，合作路径只按当前通道计算。

### 阶段 B：选择性多 Agent

1. 实现确定性异常路由器和盲复评 schema。
2. 先 Shadow 运行，记录主评/复评分歧，不改变线上结果。
3. 再启用 Judge；仅对明确触发样本生效。

### 阶段 C：下游交接

1. 增加 `LeadHandoffAssembler` 和版本化 `handoff_report` 存储。
2. 将开发策略与邮件拆成两个节点并实施字段级输入权限。
3. 增加逐句引用校验和 `doNotClaim` 拦截。

建议的验收指标：实体识别准确率不低于 99%，引用精确率不低于 98%，不存在虚构 evidence ID，执行失败转 0 次数为 0，硬门槛假阴性不高于 2%，评分维度平均误差不超过 1 个等级，严重错评较单 Agent 基线降低至少 50%。同时监控 Top 10 翻转率、复评触发率、Judge 使用率、单条成本和 P95 延迟。

## 五、本轮边界

v1.6 排行榜使用冻结共享证据做统一、可复现的回溯重评分，用来修复旧版继承分数和通道处理不一致。它不代表生产环境已经实际运行上述多 Agent 或 handoff 工作流。生产改造应按阶段 A、B、C 分开提交和验证，避免一次性改变补证、评分和邮件三个关键链路后无法定位回归来源。
