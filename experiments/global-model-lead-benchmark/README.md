# Global Model Potential-Partner Search Benchmark

本实验比较不同模型服务商的原生联网搜索能力，并在相同任务下与本项目的 Sales Lead Copilot 对照。目标是发现与 Cudy Technology 高度匹配、值得销售团队新开发或拓展合作的潜在渠道客户；它不是通用推理能力测试，也不模拟网页聊天产品 UI。

## v3 当前协议

- 所有模型收到同一条中文 user prompt，并返回自然语言答案；不要求 JSON，不添加隐藏 system prompt，不追问、不续写、不自动重试。
- 被测模型只能使用服务商随模型提供的原生 Web Search/grounding。禁止向模型注入 Codex 搜索结果、Tavily、爬虫、第三方搜索 API、联系人数据库、CRM、历史线索或其他模型输出。
- 关闭或降至服务支持的最低推理模式，使用已确认的快速模型：OpenAI `gpt-5.6-terra`、Claude `claude-haiku-4-5`、Kimi `kimi-k2.6`、DeepSeek `deepseek-v4-flash`、Grok `grok-4.3`。Gemini 保留接口但在凭证配置前不参与。
- 每次模型运行有 12 次原生搜索动作的目标资源预算、15 分钟硬超时、8,000 个可见输出 token 硬上限和零自动重试。不同服务商无法执行完全相同的工具调用硬上限，因此必须报告实际搜索次数、延迟和成本，不能因此修改质量分。
- 只有供应商响应中能观察到原生搜索调用的运行才进入正常候选提取。完成回答但没有原生搜索信号的运行在发现指标中记零；Codex 后验搜索不能挽救该次运行。
- v3 原始文件名含 `potential-fit-v3` 标签，不能覆盖或混入历史 v2 运行。

当前先在德国做五个模型系统及一个产品对照各三次独立重复。德国流程稳定后，再以相同协议扩展到加拿大、哥伦比亚、沙特阿拉伯、坦桑尼亚和新加坡。

## 潜客目标与关系状态

公司是否已经与 Cudy 合作不参与潜在匹配度打分。模型按渠道能力、产品互补性、市场覆盖和合作执行能力排序，无需专门搜索 Cudy 在售证据。Codex 在运行结束后把公开关系状态标记为 `confirmed_existing`、`no_public_evidence` 或 `unknown`：

- `confirmed_existing` 不加分也不扣分，但从净新增潜客主池分流到现有关系参考池；
- `no_public_evidence` 只表示没有发现公开证据，不等于确定未合作；
- 关系状态只作为诊断信息，权重始终为零。

Sales Lead Copilot 可以使用真实的 Tavily、筛选、排序、去重和联系人流程，但不能读取 CRM、历史线索或模型答案，也不能写入正式数据库。它使用同一国家、同一 prompt、相同的 15 分钟墙钟上限、零重试和前20名规则；必须单独报告查询数、外部请求数、credits、成本和失败。v3 产品对照不再为每家公司额外搜索当前 Cudy 在售证据。

## Codex 全量证据审核

全部运行结束后，Codex按冻结规则处理每个系统前20名：

1. 只抽取最终回答中的编号候选小节、编号表格行或独立加粗候选项，排除搜索计划、过程文本和正文举例。
2. 保存模型原始公司名、排名、答案片段、来源及联系人主张，再按公司域名和法律实体去重。
3. 使用公司官网、Impressum、政府或监管资料、行业协会、公开 LinkedIn 页面和可信新闻来源独立核验。LinkedIn不能作为公司有效性的唯一证据。
4. 证据收集与评分分阶段完成；评分阶段不显示模型、服务商、产品或重复轮次。
5. Codex只能核验模型明确提交的公司和联系人，不能增加新线索、补写未提交联系人或推测邮箱。若模型写错显示名称，但同一候选提交的一方官网URL能够唯一确认一家公司，可以解析并保留该线索，同时必须单独记录名称抽取错误；仅在正文提到公司、但没有相应一方官网URL的目录、多公司榜单、第三方文章，以及平台与店铺混合结果，不能据此修复。

候选必须同时通过六项门槛才能获得匹配度：提交信息可唯一解析为公司、公司真实存在、目标国家有实际业务、渠道相关、证据充分、属于独立潜在客户。任一门槛失败时不赋匹配度。名称准确性与身份可解析性分开记录，避免把可用线索的抽取错误和完全无法归属的候选混为一类。

## 匹配度与联系人评分

通过门槛的候选按100分评分：

- 渠道角色与客户触达：0–30；
- 产品与应用场景匹配：0–25；
- 目标市场覆盖：0–20；
- 合作执行能力：0–15；
- 战略互补性：0–10。

80–100 为高度匹配，65–79 为较强匹配，50–64 为可跟进，低于50为不合格。净新增潜客主池只包含关系状态不是 `confirmed_existing`、六项门槛全部通过且匹配度至少50的候选。

联系人单独评分，不影响公司匹配度：采购、渠道、销售、商务拓展、品类、产品或网络业务决策人为3分；CEO、总经理、所有者或相关高管为2分；真实但职责间接者为1分；错误归属或证据不足为0分。联系方式中，个人直联或目标业务团队入口为2分，公司通用邮箱、客服或总机为1分，错误或未核实信息为0分。

主指标为 `PotentialFitNDCG@20`、`MeanPotentialFit@20`、`Precision@20`、`QualifiedProspects@20` 和相对 `PooledRecall`。公司关系状态、联系人质量、来源支持、延迟、搜索次数和成本均单独报告，不能混入匹配度。

## 人工盲审与Codex验收

Codex先审核合并池中的全部候选和联系人。之后自动生成不含Codex分数和系统身份的公司级人工盲审包：

- 德国首轮抽取25%，且不少于12个候选；
- 分层覆盖无效、低匹配、可跟进、较强和高度匹配候选；
- 人工审核公司身份、六项门槛、关系状态和匹配度；联系人身份可以作为上下文展示，但不要求人工评分，联系方式不进入人工审核；
- 联系人和联系方式继续由Codex全量核验并独立报告，不影响公司匹配度；
- 有身份歧义、证据冲突、阈值临界或其他风险标记的候选进入额外风险盲审队列，补充量不超过候选池的10%，且不混入统计样本的一致性估计。

Codex公司初审通过条件为：合格状态一致率至少90%、匹配分档一致率至少80%、加权Kappa至少0.75、匹配度平均绝对误差不超过10分。联系人和联系方式不参与人机一致性验收。未达到任一门槛时，系统给出追加相当于候选池15%的盲审样本；规则修订后必须重评全部候选。

## 运行流程

1. `npm run benchmark:verify`：离线验证 prompt、请求结构、协议隔离、评分和抽样规则。
2. `npm run benchmark:preflight -- <provider>`：每家一次最小基础请求及一次原生搜索探针；失败不重试。
3. 用户另行确认付费调用后，执行 `npm run benchmark:pilot -- <provider> <repetition>`。
4. 产品对照使用 `npm run benchmark:product -- <repetition>`。
5. 所有运行结束后执行 `npm run benchmark:prepare-review`，生成本地证据池。
6. Codex完成公开网页核验并执行 `npm run benchmark:apply-verification`。
7. Codex按照 `lib/codex-audit.ts` 写入完整的 `reviews/working/codex-assessments.local.json`。
8. `npm run benchmark:prepare-human-audit`：生成25%统计样本、风险补充样本、盲审Markdown及空白评分JSON。
9. 用户完成盲审后，将结果保存为 `human-audit-decisions.local.json`，执行 `npm run benchmark:evaluate-human-audit`。

## 历史 v2 德国试验

2026-08-20 的 v2 德国结果是评测管线试验，不是最终潜客搜索排行榜。15次模型调用中有10次产生可评分的原生搜索答案、1次没有搜索而记零、4次基础设施失败；产品对照两次成功、一次因 Tavily 限流失败。合并池共有79次候选出现和48个去重候选。

v2 prompt同时搜索现有和潜在 Cudy 渠道，旧评分又把当前 Cudy 渠道设为最高等级，因此与当前“高匹配净新增潜客”目标不一致。现有原始结果只用于验证Codex审核机制，不能与v3结果合并或发布为最终模型质量榜。详情见 `reports/2026-08-20-v2-protocol-status.json`。

## 文件与隐私

- `prompts/native-search-potential-partners-v3.md`：冻结的v3自然语言user prompt；
- `config/pilot.json`：当前协议、运行范围和硬上限；
- `config/judging.json`：潜客匹配、联系人评分和人工验收门槛；
- `lib/codex-audit.ts`：证据门槛、匹配度、关系分流、盲审抽样及一致性计算；
- `reports/2026-08-20-v2-protocol-status.json`：不与v3合并的历史试验状态。

API密钥只能保存在 `.env.local`。原始回答、候选公司、联系方式、盲化盐、Codex评分、人工审核决定和分歧记录都保留在被Git忽略的本地目录；仓库只提交协议、代码、测试和脱敏聚合报告。
